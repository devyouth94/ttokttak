# Notification Phase Checkpoints

이 문서는 17~19단계 알림 구현을 바로 진행하기 위한 세부 체크포인트다.
제품 범위는 `PRODUCT_SPEC.md`를 따른다.
구성요소 책임과 데이터 흐름은 `SYSTEM_DESIGN.md`를 따른다.
동기화 규칙과 경계 조건은 `DOMAIN_LOGIC.md`를 따른다.
상위 구현 순서는 `IMPLEMENTATION_PLAN.md`를 따른다.

## 1. 공통 원칙

- 서버 데이터가 source of truth다.
- 현재 기기 기준으로만 로컬 알림을 예약하고 취소한다.
- 알림 예약 범위는 앞으로 14일이다.
- 권한 거부 상태여도 서버 데이터는 유지한다.
- 예약 metadata는 device-scoped로 관리한다.
- phase 16에서 고정한 미래 예약 경계를 유지한다.

## 2. 17단계: 알림 권한 및 시작 시 동기화

### 목표

- 권한 상태를 앱에서 일관되게 해석한다.
- 앱 시작과 세션 복원 시 동기화 진입점을 만든다.

### 작업 체크포인트

- [x] 권한 상태 모델을 정리한다.
- [x] 권한 조회 로직을 공통 경로로 묶는다.
- [x] 권한 요청 플로우를 정의한다.
- [x] 권한 거부 시 설정 이동 경로를 연결한다.
- [x] 앱 시작 시 1회 동기화 조건을 정의한다.
- [x] 세션 복원 시 동기화 조건을 정의한다.
- [x] 중복 실행 방지 기준을 정리한다.

### 완료 기준

- [x] 권한 허용, 거부, 미지원 상태를 구분할 수 있다.
- [x] 앱 시작 시 조건부 동기화가 실행된다.
- [x] 세션 복원 후 조건부 동기화가 실행된다.
- [x] 권한 거부 상태에서 설정 이동 경로가 노출된다.

### 검증 시나리오

- [x] 권한 허용 상태에서 앱 시작 시 동기화가 트리거된다.
- [x] 권한 거부 상태에서 안내와 설정 이동 경로가 보인다.
- [x] 앱이 포그라운드로 돌아오면 권한 상태가 다시 반영된다.

## 3. 18단계: 변경 시 알림 동기화

### 목표

- 데이터 변경 뒤 현재 기기 알림이 다시 맞춰진다.
- 미래 occurrence만 재조정한다.

### 작업 체크포인트

- [x] 항목 생성 후 동기화 경로를 연결한다.
- [x] 항목 수정 후 동기화 경로를 연결한다.
- [x] 완료 처리 후 동기화 경로를 연결한다.
- [x] 건너뜀 처리 후 동기화 경로를 연결한다.
- [x] 보관 또는 삭제 후 동기화 경로를 연결한다.
- [x] item edit 시 `effective_from_utc` 이후 미래 예약만 재조정한다.
- [x] 실패 시 재시도 가능한 동기화 경로를 남긴다.

### 완료 기준

- [x] create, update, complete, skip, archive 이후 동기화 여부가 코드에서 일관된다.
- [x] 수정 이후 과거 예약은 유지된다.
- [x] 실패가 조용히 묻히지 않고 재시도 경로가 있다.

### 검증 시나리오

- [ ] 항목 생성 후 새 예약이 반영된다.
- [ ] 항목 수정 후 미래 예약만 다시 계산된다.
- [ ] 완료 처리 후 관련 예약이 정리된다.
- [ ] 건너뜀 처리 후 관련 예약이 정리된다.

## 4. 19단계: 디바이스 범위 알림 영속화

### 목표

- 현재 기기 예약과 DB metadata가 일관되게 맞는다.
- 중복 없이 upsert와 delete가 동작한다.

### 작업 체크포인트

- [ ] 현재 기기의 기존 reservation metadata 조회 경로를 정리한다.
- [ ] 유효하지 않은 reservation 판정 기준을 정리한다.
- [ ] 유효하지 않은 reservation 취소 경로를 연결한다.
- [ ] 새 reservation 생성 경로를 연결한다.
- [ ] `device_notification_reservations` upsert 규칙을 고정한다.
- [ ] `device_notification_reservations` delete 규칙을 고정한다.
- [ ] `(device_id, item_id, scheduled_at_utc)` 기준 중복 방지 규칙을 유지한다.
- [ ] 로컬 notification id와 metadata 매핑을 검증한다.

### 완료 기준

- [ ] 현재 기기 metadata만 갱신된다.
- [ ] 무효 reservation metadata가 삭제된다.
- [ ] 새 reservation 결과가 중복 없이 upsert된다.
- [ ] 동일 occurrence가 중복 저장되지 않는다.

### 검증 시나리오

- [ ] 기존 metadata와 로컬 예약을 비교해 무효 항목을 찾을 수 있다.
- [ ] 무효 예약 취소 후 metadata도 함께 정리된다.
- [ ] 신규 예약 생성 후 metadata가 upsert된다.
- [ ] 같은 기기에서 동일 occurrence가 중복 저장되지 않는다.

## 5. 최종 확인 순서

- [x] 17단계 완료 후 권한 상태와 시작 동기화 진입점이 안정적으로 동작한다.
- [ ] 18단계 완료 후 주요 mutation 뒤 알림이 다시 맞춰진다.
- [ ] 19단계 완료 후 현재 기기 예약과 metadata가 일치한다.
- [ ] 17~19단계 전체 완료 후 알림 상태가 앱 재시작 뒤에도 일관되게 유지된다.
